# 交通信号控制平台需求规格说明书

## 1. 项目概述

项目名称：交通信号控制平台

仿真地点：天津市河东区新开路与华龙道交叉口。

项目目标：建立一个能够通过浏览器控制交通信号灯，并通过SUMO模拟机动车运行情况的单路口信控平台。

## 2. 仿真场景需求

### 2.1 道路

- 模拟一个完整的十字路口。
- 包含新开路南北方向道路。
- 包含华龙道东西方向道路。
- 包含路口进口道和出口道。
- 道路应具有合理的车道连接关系。

### 2.2 车道

- 支持机动车直行车道。
- 支持机动车左转车道。
- 支持机动车右转车道。
- 根据实际道路条件确定车道数量及转向关系。
- 车道应关联正确的交通信号控制关系。

### 2.3 机动车

- 支持机动车自动生成。
- 支持机动车直行、左转、右转。
- 支持机动车跟车行驶。
- 红灯时车辆应在停止线前停车。
- 绿灯时允许符合通行规则的车辆通过。
- 黄灯期间按照SUMO车辆行为及停车安全规则处理。
- 浏览器实时显示机动车位置和运动状态。

## 3. 交通信号灯需求

### 3.1 基本灯色

- 红灯：禁止通行。
- 黄灯：警示及过渡。
- 绿灯：允许通行。

### 3.2 信号灯控制

- 信号灯由信号机统一控制。
- 支持南北方向和东西方向信号控制。
- 同一通行方向内的受控车道按照相位方案执行。
- 不允许冲突方向同时获得冲突性通行权。
- 支持相位切换和配时调整。

## 4. 信号灯控制需求

### 4.1 配时参数

平台支持分别配置南北方向和东西方向的绿灯、黄灯持续时间。

| 参数       | 示例值         | 约束     |
| -------- | ----------- | ------ |
| 南北绿灯持续时间 | 30秒、40秒、60秒 | 必须大于8秒 |
| 东西绿灯持续时间 | 30秒、40秒、60秒 | 必须大于8秒 |
| 南北黄灯持续时间 | 默认3秒        | 必须大于0秒 |
| 东西黄灯持续时间 | 默认3秒        | 必须大于0秒 |

上述数值为配置示例，不是固定限制。

红灯持续时间由对向绿灯和黄灯持续时间自动计算，不作为独立配置参数：

- 南北红灯总时长 = 东西绿灯持续时间 + 东西黄灯持续时间。

- 东西红灯总时长 = 南北绿灯持续时间 + 南北黄灯持续时间。

系统必须校验南北、东西两个方向的红灯总时长均大于10秒。

### 4.2 红灯规则

1. 红灯持续时间由对向绿灯和黄灯阶段共同决定。

2. 红灯剩余时间大于10秒时，不显示末段倒计时。

3. 红灯剩余时间进入最后10秒时开始倒计时。

4. 倒计时显示10、9、8……1。

5. 倒计时结束后直接切换为绿灯。

6. 红灯总时长必须大于10秒。

7. 红灯倒计时必须与对应方向下一次绿灯开始时刻保持一致。

### 4.3 绿灯规则

1. 南北、东西绿灯持续时间分别由平台配置。

2. 绿灯剩余时间大于8秒时，不显示末段倒计时。

3. 绿灯剩余时间进入最后8秒时开始倒计时。

4. 倒计时显示8、7、6……1。

5. 此阶段信号灯仍保持绿色。

6. 绿灯倒计时结束后进入对应方向黄灯。

7. 绿灯总时长必须大于8秒。

### 4.4 黄灯规则

1. 南北、东西黄灯持续时间分别配置，默认均为3秒。

2. 黄灯全程显示倒计时。

3. 黄灯倒计时显示3、2、1。

4. 黄灯结束后，对应方向切换为红灯，对向方向切换为绿灯。

5. 黄灯期间不允许新的车辆进入受控冲突区域。

6. 黄灯实际持续时间必须与后端配置及SUMO信号状态一致。

### 4.5 相位控制规则

第一版采用南北、东西两个基本通行相位：

- 南北绿灯、东西红灯。

- 南北黄灯、东西红灯。

- 南北红灯、东西绿灯。

- 南北红灯、东西黄灯。

相位循环顺序：

南北绿灯 → 南北黄灯 → 东西绿灯 → 东西黄灯 → 南北绿灯。

必须满足：

1. 南北绿灯结束后必须经过南北黄灯，才能进入东西绿灯。

2. 东西绿灯结束后必须经过东西黄灯，才能进入南北绿灯。

3. 黄灯结束后，对应方向必须进入红灯。

4. 对向方向的红灯持续时间必须覆盖另一方向的绿灯和黄灯阶段。

5. 冲突方向不能同时获得通行权。

6. 当前方案不额外增加全红阶段。如果道路冲突分析或安全验证要求增加全红清空时间，必须通过正式设计变更实施。

7. 后续根据实际车道和转向冲突关系扩展独立左转相位。

### 4.6 配时修改

- 平台支持修改南北绿灯持续时间。

- 平台支持修改东西绿灯持续时间。

- 平台支持修改南北黄灯持续时间。

- 平台支持修改东西黄灯持续时间。

- 红灯持续时间由系统根据对向绿灯和黄灯配置自动计算。

- 平台支持查看当前生效的配时方案。

- 平台支持查看待生效的配时方案。

- 平台支持查看修改前后的配时参数。

- 运行期间修改配时，当前正在执行的信号阶段不得被突然截断。

- 新配置从下一次进入对应信号阶段时生效。

- 后端必须校验新配置及计算得到的红灯时长是否合法。

- 不允许修改配时导致后端状态机与SUMO信号状态不一致。

- 配时修改需要记录操作时间及修改内容。

## 5. 信号机控制需求

### 5.1 基础控制

- 启动信号机。
- 停止信号机。
- 查询当前运行状态。
- 查询当前相位。
- 查询当前灯色。
- 查询剩余时间。
- 手动切换相位。
- 修改相位配时。

### 5.2 状态信息

信号机至少需要提供：

- 信号机编号。
- 当前运行状态。
- 当前相位编号。
- 当前通行方向。
- 当前灯色。
- 当前阶段剩余时间。
- 下一阶段。
- 当前配时方案。

### 5.3 控制安全

- 手动控制必须经过后端校验。
- 禁止冲突方向同时放行。
- 信号切换必须符合相位安全规则。
- 控制异常时记录日志。
- 浏览器断开连接不得导致信号机失控。

## 6. 浏览器可视化需求

### 6.1 路口展示

- 展示完整十字路口。
- 展示道路和车道。
- 展示停止线。
- 展示交通信号灯。
- 展示机动车。
- 展示车辆实时行驶方向。

### 6.2 信号灯展示

- 红灯显示红色。
- 黄灯显示黄色。
- 绿灯显示绿色。
- 显示红灯末段倒计时。
- 显示绿灯末段倒计时。
- 显示黄灯倒计时。

### 6.3 信号控制面板

- 展示信号机运行状态。
- 展示当前相位。
- 展示当前配时。
- 提供红灯、绿灯、黄灯时长配置。
- 提供仿真启动和停止操作。
- 提供手动相位控制。
- 显示操作结果及错误信息。

### 6.4 实时性

- 后端统一产生信号状态和剩余时间。
- 通过WebSocket向浏览器推送状态。
- 浏览器不得独立维护一套信号控制计时逻辑。
- 车辆位置与信号灯状态应保持仿真时间一致。

## 7. 后端接口需求

第一版规划以下接口：

| 接口                                   | 功能       |
| ------------------------------------ | -------- |
| GET /api/health                      | 服务健康检查   |
| GET /api/simulation/status           | 仿真运行状态   |
| POST /api/simulation/start           | 启动仿真     |
| POST /api/simulation/stop            | 停止仿真     |
| GET /api/signals                     | 查询信号机    |
| GET /api/signals/{id}/state          | 查询信号状态   |
| GET /api/signals/{id}/phases         | 查询相位     |
| POST /api/signals/{id}/phases/switch | 手动切换相位   |
| GET /api/signals/{id}/timing         | 查询配时     |
| PUT /api/signals/{id}/timing         | 修改配时     |
| WS /ws/simulation                    | 实时仿真状态推送 |

具体请求和响应模型在API设计文档中定义。

## 8. 数据持久化需求

需要保存：

- 路口基本信息。
- 道路信息。
- 车道信息。
- 信号机信息。
- 信号灯信息。
- 相位配置。
- 配时方案。
- 仿真运行记录。
- 信号控制操作记录。

## 9. 部署需求

- 支持Windows开发环境。
- 支持Docker Compose部署。
- SUMO及其TraCI运行环境需要明确配置。
- 前端、后端及数据库具备独立服务配置。
- 提供环境变量示例。
- 提供可复现启动和停止命令。

## 11. 第一版范围

第一版只实现一个十字路口。

优先完成南北、东西两个基本通行相位。

优先保证信号控制正确、机动车通行正确、倒计时准确及浏览器实时展示。

复杂自适应控制、多路口协调控制暂不纳入第一版。
