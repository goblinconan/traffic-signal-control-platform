# 交通信号控制平台需求规格说明书

## 1. 项目概述

项目名称：交通信号控制平台

仿真地点：天津市河东区新开路与华龙道交叉口。

项目目标：建立一个能够通过浏览器控制交通信号灯，并通过SUMO模拟机动车运行情况的单路口信控平台。

## 2. 仿真场景需求

### 2.1 道路

- 模拟一个完整的十字路口。
- 包含新开路南北方向道路。
- 包含华龙道东西方向道路。
- 包含路口进口道和出口道。
- 道路应具有合理的车道连接关系。

### 2.2 车道

- 四个进口方向均应分别设置机动车左转、直行和右转专用车道。
- 左转车道不得与直行或右转车道共用。
- 直行车道不得与左转或右转车道共用。
- 右转车道不得与左转或直行车道共用。
- 按本项目目标交通组织，每个进口方向至少需要 3 条对应转向的独立机动车车道；实际道路资料与目标模型不一致时，必须记录差异及仿真假设。
- 每条车道必须关联正确的 SUMO lane、转向连接、信号组或让行控制规则。
- 车道编号不得被业务逻辑直接假设为固定转向；必须通过路网连接关系识别。

### 2.3 机动车

- 支持机动车自动生成。
- 支持机动车直行、左转、右转。
- 支持机动车跟车行驶、减速、停车和安全让行。
- 受保护左转及直行车辆必须服从对应信号组。
- 红灯时，受红灯控制的直行和左转车辆应在停止线前停车。
- 绿灯时，允许符合对应信号组放行规则的车辆通过。
- 黄灯期间按照 SUMO 车辆行为及停车安全规则处理，不得跳过黄灯阶段。
- 右转车辆使用独立右转车道；即使对应方向的直行/左转信号为红灯，也允许在安全让行条件下右转。
- 右转车辆接近冲突区域时必须减速观察；若行人、非机动车或其他冲突交通流正在通过或即将进入冲突区域，必须停车等待。
- 只有确认冲突解除后，右转车辆才可继续通行；不得因右转允许在红灯期间通行而获得优先权。
- 浏览器实时显示机动车位置和运动状态。

## 3. 交通信号灯需求

### 3.1 基本灯色

- 红灯：禁止通行。
- 黄灯：警示及过渡。
- 绿灯：允许通行。

### 3.2 信号灯控制

- 信号灯由统一信号机控制器管理。
- 南北方向左转、南北方向直行、东西方向左转、东西方向直行分别作为独立受保护信号组。
- 南北两个相反方向的左转同时放行；东西两个相反方向的左转同时放行。该同时放行关系以用户确认的交通组织为设计前提，仍须通过 SUMO 实际连接和冲突矩阵验证。
- 左转放行期间，对应方向直行信号必须为红灯。
- 直行放行期间，对应方向左转信号必须为红灯。
- 右转使用四个进口方向各自的独立车道，采用让行通行规则，不并入左转或直行的保护式绿灯阶段。
- 不允许冲突交通流同时获得冲突性优先通行权。
- 支持相位切换、配时调整、AUTO/MANUAL 模式和控制启用/停用。

## 4. 信号灯控制需求

### 4.1 配时参数

第一版分别配置以下四类受保护交通流的绿灯和黄灯持续时间：

| 交通流   | 绿灯字段            | 黄灯字段             | 当前测试基线 | 约束                 |
| -------- | ------------------- | -------------------- | -----------: | -------------------- |
| 南北直行 | `ns_straight_green` | `ns_straight_yellow` |     40s / 3s | 绿灯 > 8s；黄灯 > 0s |
| 南北左转 | `ns_left_green`     | `ns_left_yellow`     |     20s / 3s | 绿灯 > 8s；黄灯 > 0s |
| 东西直行 | `ew_straight_green` | `ew_straight_yellow` |     40s / 3s | 绿灯 > 8s；黄灯 > 0s |
| 东西左转 | `ew_left_green`     | `ew_left_yellow`     |     20s / 3s | 绿灯 > 8s；黄灯 > 0s |

表中时长是当前 SUMO 测试基线，不是不可修改的固定值。四类绿灯和黄灯均可独立配置；黄灯默认 3 秒。

红灯持续时间不作为独立输入参数，由后端根据完整周期和实际阶段顺序计算。若第一版不设置额外全红清空阶段，周期长度为：

`C = Σ(四类交通流各自的绿灯时长 + 黄灯时长)`

每类受保护信号组的红灯总时长为周期内其他三类交通流的绿灯与黄灯时长之和。例如：

- `R_NS_STRAIGHT = (G_NS_LEFT + Y_NS_LEFT) + (G_EW_STRAIGHT + Y_EW_STRAIGHT) + (G_EW_LEFT + Y_EW_LEFT)`
- `R_NS_LEFT = (G_NS_STRAIGHT + Y_NS_STRAIGHT) + (G_EW_STRAIGHT + Y_EW_STRAIGHT) + (G_EW_LEFT + Y_EW_LEFT)`
- `R_EW_STRAIGHT = (G_NS_STRAIGHT + Y_NS_STRAIGHT) + (G_NS_LEFT + Y_NS_LEFT) + (G_EW_LEFT + Y_EW_LEFT)`
- `R_EW_LEFT = (G_NS_STRAIGHT + Y_NS_STRAIGHT) + (G_NS_LEFT + Y_NS_LEFT) + (G_EW_STRAIGHT + Y_EW_STRAIGHT)`

四类受保护信号组的红灯总时长均必须大于 10 秒。若冲突分析最终要求增加全红清空阶段，该阶段必须纳入周期和红灯时长计算，不能继续使用忽略全红时间的简化公式。

右转采用独立让行规则，不纳入上述四类保护式配时字段，也不使用普通红灯末段倒计时规则。

### 4.2 红灯规则

1. 红灯总时长由完整周期中其他受保护信号组的绿灯、黄灯阶段及可能存在的全红清空阶段共同决定。
2. 四类受保护信号组的红灯总时长必须分别大于 10 秒。
3. 红灯剩余时间大于 10 秒时，不显示末段倒计时。
4. 红灯剩余时间进入最后 10 秒时开始倒计时。
5. 倒计时显示 10、9、8……1。
6. 倒计时结束后，在合法阶段边界切换到该信号组的下一次绿灯。
7. 红灯倒计时必须与后端状态机和 SUMO 对应连接的下一次绿灯开始时刻一致。
8. 右转让行通行不按普通受控红灯处理；不得因主方向红灯倒计时而禁止符合让行条件的右转车辆通行。

### 4.3 绿灯规则

1. 南北直行、南北左转、东西直行、东西左转四类信号组分别配置绿灯持续时间。
2. 每类绿灯持续时间必须大于 8 秒。
3. 绿灯剩余时间大于 8 秒时，不显示末段倒计时。
4. 绿灯剩余时间进入最后 8 秒时开始倒计时。
5. 倒计时显示 8、7、6……1；倒计时期间信号灯仍保持绿色。
6. 绿灯倒计时结束后进入该信号组对应的黄灯阶段。
7. 左转绿灯期间，同一方向直行信号必须保持红灯；直行绿灯期间，同一方向左转信号必须保持红灯。

### 4.4 黄灯规则

1. 四类受保护信号组分别配置黄灯持续时间，默认均为 3 秒。
2. 黄灯持续时间必须大于 0 秒。
3. 黄灯全程显示倒计时；默认倒计时显示 3、2、1。
4. 每个绿灯阶段结束后必须完整执行对应黄灯阶段。
5. 黄灯结束后，该信号组转为红灯，并按阶段顺序进入下一业务阶段。
6. 黄灯期间不允许新的车辆进入受控冲突区域；车辆是否停车按 SUMO 的停车安全规则处理。
7. 黄灯实际持续时间必须与后端配置及 SUMO 信号状态一致。

### 4.5 相位控制规则

第一版包含四类受保护业务通行阶段，每个绿灯阶段后紧接对应黄灯阶段，共形成 8 个 SUMO 信号阶段：

1. 南北左转绿灯 → 南北左转黄灯。
2. 南北直行绿灯 → 南北直行黄灯。
3. 东西左转绿灯 → 东西左转黄灯。
4. 东西直行绿灯 → 东西直行黄灯。
5. 循环返回南北左转绿灯。

每个业务阶段中，两个相反方向的同类交通流同时放行：南北直行同时放行、南北左转同时放行、东西直行同时放行、东西左转同时放行。

必须满足：

1. 南北左转绿灯期间，南北直行、东西直行和东西左转等受保护冲突信号组均保持红灯。
2. 南北直行绿灯期间，南北左转及东西方向受保护信号组保持红灯。
3. 东西左转绿灯期间，东西直行、南北直行和南北左转等受保护冲突信号组均保持红灯。
4. 东西直行绿灯期间，东西左转及南北方向受保护信号组保持红灯。
5. 每个绿灯阶段结束后必须经过完整黄灯阶段，不能直接跳转或被手动命令截断。
6. 任意两个存在冲突的受保护交通流不得同时获得优先通行权。
7. 四个方向的右转车辆不占用上述保护式阶段，但只能按独立让行规则通行。
8. 当前文档暂不固化额外全红清空阶段；是否需要全红时间必须由实际路网冲突矩阵和安全验证决定，并通过设计变更记录。
9. 最终 SUMO 状态字符串必须按 `getControlledLinks()` 和实际冲突关系生成，不得将业务表格列号直接当作 `linkIndex`。

### 4.6 配时修改

- 平台分别支持修改南北直行、南北左转、东西直行、东西左转四类绿灯持续时间。
- 平台分别支持修改上述四类信号组的黄灯持续时间。
- 红灯持续时间由系统根据完整周期、实际阶段顺序及全红清空时间（如经批准设置）自动计算。
- 平台支持查看当前生效的配时方案和待生效配时方案。
- 平台支持查看修改前后的配时参数。
- 运行期间修改配时，当前正在执行的绿灯或黄灯阶段不得被突然截断。
- 新配置必须在约定的安全边界整体生效，不得在同一周期内混用不同配时版本。
- 后端必须校验四类绿灯、四类黄灯和计算得到的四类红灯时长。
- 不允许修改配时导致后端状态机与 SUMO 信号状态不一致。
- 配时修改需要记录操作时间、修改内容、提交结果及生效时机。

## 5. 信号机控制需求

### 5.1 基础控制

- 启动、停止信号机控制。
- 查询当前运行状态、控制启用状态和控制模式。
- 查询当前业务阶段、SUMO 阶段索引、各信号组灯色及剩余时间。
- 查询下一阶段及当前配时方案版本。
- 支持 AUTO（自动）和 MANUAL（手动）模式切换。
- MANUAL 模式支持提交目标业务阶段请求。
- 支持修改四类受保护信号组的配时。

### 5.2 状态信息

信号机至少需要提供：

- 信号机编号。
- 仿真运行状态。
- 信号控制启用状态。
- 当前控制模式（AUTO/MANUAL）。
- 当前业务阶段编号及 SUMO 阶段索引。
- 四类受保护信号组当前灯色及剩余时间。
- 四个进口方向的右转让行状态。
- 当前阶段剩余时间、下一阶段及当前配时方案版本。

### 5.3 控制安全

- 手动控制必须经过后端校验。
- 手动请求不得直接向 SUMO 写入任意状态字符串。
- 手动请求不得跳过或缩短正在执行的黄灯阶段。
- 禁止冲突的受保护交通流同时获得优先通行权。
- 右转车辆必须遵循减速观察及冲突让行规则。
- 仿真运行状态、信号控制启用状态和 AUTO/MANUAL 模式必须分别管理。
- 控制异常时记录日志；浏览器断开连接不得导致信号控制器失控。

## 6. 浏览器可视化需求

### 6.1 路口展示

- 展示完整十字路口、道路和独立左转/直行/右转车道。
- 展示停止线、交通信号灯、机动车和车辆实时行驶方向。
- 右转车道及右转车辆应与直行、左转车道清晰区分。

### 6.2 信号灯展示

- 展示红、黄、绿灯及四类受保护信号组。
- 显示红灯末段倒计时、绿灯末段倒计时和黄灯倒计时。
- 对右转让行状态进行明确区分，不得把让行通行显示为具有优先权的普通绿灯。
- 展示当前阶段、下一阶段和剩余时间。

### 6.3 信号控制面板

- 展示仿真运行状态、信号控制 ENABLED/DISABLED 和 AUTO/MANUAL 模式。
- 展示当前阶段和当前配时。
- 提供四类绿灯、四类黄灯时长配置。
- 提供仿真启动、停止及信号控制启用/停用操作。
- 在 MANUAL 且状态允许时提供手动阶段控制。
- 显示操作结果、失败原因及待生效配时。

### 6.4 实时性与双视图

- 后端统一产生信号状态和剩余时间，通过 WebSocket 推送。
- 浏览器不得独立维护信号控制计时逻辑。
- 车辆位置与信号灯状态应保持仿真时间一致。
- 保留现有二维 SVG 路口视图，增加二维/三维视图切换。
- 二维和三维视图共用同一份后端网络数据、仿真状态和 WebSocket 数据。
- 视图切换不得重启仿真、重置信号状态或改变控制模式。

## 7. 后端接口需求

第一版规划以下接口：

| 接口                                 | 功能             |
| ------------------------------------ | ---------------- |
| GET /api/health                      | 服务健康检查     |
| GET /api/simulation/status           | 仿真运行状态     |
| POST /api/simulation/start           | 启动仿真         |
| POST /api/simulation/stop            | 停止仿真         |
| GET /api/signals                     | 查询信号机       |
| GET /api/signals/{id}/state          | 查询信号状态     |
| GET /api/signals/{id}/phases         | 查询相位         |
| POST /api/signals/{id}/phases/switch | 手动切换相位     |
| GET /api/signals/{id}/timing         | 查询配时         |
| PUT /api/signals/{id}/timing         | 修改配时         |
| WS /ws/simulation                    | 实时仿真状态推送 |

具体请求和响应模型在API设计文档中定义。

## 8. 数据持久化需求

需要保存：

- 道路信息。
- 车道信息。
- 信号机信息。
- 信号灯信息。
- 相位配置。
- 配时方案。
- 仿真运行记录。
- 信号控制操作记录。

- 支持Windows开发环境。
- 支持Docker Compose部署。
- SUMO及其TraCI运行环境需要明确配置。
- 前端、后端及数据库具备独立服务配置。
- 提供环境变量示例。
- 提供可复现启动和停止命令。

## 10. 功能验收标准

### 10.1 仿真场景与车道

- [ ] SUMO 可以加载目标十字路口网络。
- [ ] 四个进口方向分别具有独立左转、直行、右转车道。
- [ ] 车道与 SUMO lane、连接关系和业务转向映射正确。
- [ ] 机动车能够按路线直行、左转、右转。
- [ ] 受红灯控制的直行和左转车辆能够在停止线前停车。

### 10.2 信号控制与配时

- [ ] 四类受保护业务阶段按 0→1→2→3→4→5→6→7→0 的 8 个 SUMO 阶段顺序运行。
- [ ] 南北两个方向的左转同时放行，且南北直行保持红灯。
- [ ] 东西两个方向的左转同时放行，且东西直行保持红灯。
- [ ] 四类绿灯持续时间分别可配置且均大于 8 秒。
- [ ] 四类黄灯持续时间分别可配置，默认 3 秒且必须大于 0。
- [ ] 四类受保护信号组红灯总时长按完整周期计算且均大于 10 秒。
- [ ] 红灯结束前 10 秒准确倒计时。
- [ ] 绿灯结束前 8 秒准确倒计时。
- [ ] 黄灯全程倒计时且持续时间准确。
- [ ] 配时修改不截断当前阶段，并在约定安全边界整体生效。
- [ ] 冲突的受保护交通流不会同时获得优先通行权。

### 10.3 右转安全让行

- [ ] 四个进口方向均有独立右转车道。
- [ ] 对应方向红灯期间，右转车辆仍可按让行规则通行。
- [ ] 右转车辆接近冲突区域时会减速观察。
- [ ] 行人或非机动车正在通过或即将进入冲突区域时，右转车辆必须停车等待；确认冲突解除后方可通行。
- [ ] 存在其他冲突交通流正在通过或即将进入冲突区域时，右转车辆必须停车等待；确认冲突解除后方可通行。
- [ ] 冲突解除后，右转车辆能够恢复通行。
- [ ] 右转行为通过真实 SUMO 场景验证，不能只验证静态灯色字符串。

### 10.4 控制台与双视图

- [ ] 浏览器能够展示实时路口和车辆。
- [ ] 浏览器能够展示四类受保护信号组及右转让行状态。
- [ ] 浏览器能够启动、停止仿真及启用、停用信号控制。
- [ ] 浏览器能够切换 AUTO/MANUAL。
- [ ] MANUAL 模式下能够提交合法阶段请求，且不能绕过黄灯。
- [ ] 浏览器能够修改并查询四类绿灯、黄灯配时。
- [ ] 二维视图原有功能保持可用。
- [ ] 能够切换三维视图并返回二维，且两种视图数据一致。

## 11. 第一版范围

第一版只实现一个十字路口，包含四个进口方向的独立左转、直行、右转车道。

信号控制采用四类受保护业务通行阶段及其黄灯过渡，共 8 个 SUMO 阶段；南北、东西相反方向的同类左转同时放行。

右转始终采用独立让行规则，在任意信号阶段均必须减速观察，并让行行人、非机动车及其他冲突交通流；只有确认冲突解除后才可继续通行。

第一版还包括 AUTO/MANUAL 控制模式、独立的信号控制启用/停用、浏览器控制台，以及保留二维并增加三维视图切换。

复杂自适应控制、多路口协调控制暂不纳入第一版。

## 12. 当前信号相位基线

### 12.1 八阶段方案

SUMO 索引 阶段名称 南北左转 南北直行 东西左转 东西直行

1 NS_LEFT_YELLOW 黄 红 红 红
2 NS_STRAIGHT_GREEN 红 绿 红 红

6 EW_STRAIGHT_GREEN 红 红 红 绿
7 EW_STRAIGHT_YELLOW 红 红 红 黄

阶段顺序按 0→1→2→3→4→5→6→7→0 循环。每个南北信号组代表南、北两个相反方向的同类交通流；每个东西信号组代表东、西两个相反方向的同类交通流。

四个方向各自设置独立右转车道。右转不属于上述八阶段中的受保护放行阶段，而是始终采用独立让行规则，不获得优先通行权。右转车辆必须减速观察，并让行行人、非机动车及其他冲突交通流。当前 SUMO TLS 程序将四个右转连接（linkIndex 0、5、10、15）在全部八个阶段设置为小写 `g`，表示让行绿灯，而不是受保护绿灯或无条件通行。最终让行行为及冲突区域安全性必须通过实际 controlled-links、冲突矩阵和车辆轨迹验证。

验收仍然必须检查：

- 实际 controlled-links。
- TLS 冲突关系。
- 右转车辆接近冲突区时的速度变化。
- 行人、非机动车及其他冲突交通流出现时是否停车。
- 冲突解除后是否恢复通行。

表中 40s/20s/3s 是当前 SUMO 测试基线，不代表最终交通配时已经验收。每个 linkIndex 的灯色必须依据 `getControlledLinks()` 映射生成，不可把表格列直接当作 SUMO 状态字符串下标。

### 12.2 黄灯与相位过渡

- 每个绿灯阶段结束后必须完整执行对应黄灯阶段。
- 手动请求不得跳过黄灯，也不得缩短正在执行的黄灯时长。
- 目标阶段必须通过合法的安全过渡路径到达。
- SUMO 实际灯色、后端状态机阶段及 WebSocket 展示必须一致。
- 当前记录的 `Missing yellow phase` 警告必须在后端控制升级验收前查明原因并通过真实 SUMO 测试；不得以静态字符串长度匹配代替过渡安全验证。
- 当前设计不擅自增加全红阶段；如冲突分析证明需要，必须另行记录设计决策，并同步调整周期和红灯计算。

## 13. 仿真与信号控制状态解耦

系统必须分别维护以下状态：

1. **仿真运行状态**：STOPPED、STARTING、RUNNING、STOPPING、ERROR。
2. **信号控制启用状态**：ENABLED、DISABLING、DISABLED（DISABLING 为安全过渡态）。
3. **控制模式**：AUTO、MANUAL。

三者不能合并成一个“启动/停止”字段。例如，仿真可以处于 RUNNING，而信号控制处于 DISABLED；控制模式也不能代替仿真运行状态。

### 13.1 自动模式

- AUTO 模式由后端状态机按配置的阶段顺序和持续时间自动推进。
- 阶段计时以 SUMO 仿真时间为准。
- 前端不自行计算或驱动相位切换。
- 配时修改遵守不截断当前阶段的规则。

### 13.2 手动模式

- MANUAL 模式允许有权限的操作员提交目标阶段请求。
- 请求必须经过后端校验，并遵循完整黄灯过渡和冲突保护。
- 手动请求不能直接向 SUMO 写入任意状态字符串。
- MANUAL 模式切入时，当前绿灯必须完成原定时长，随后完成完整黄灯，再进入全红等待。
- MANUAL 模式未收到新的合法阶段请求时必须持续全红，不得自动推进。
- 手动模式下配时修改仍需遵守当前阶段不被截断的规则。

### 13.3 控制启用/停用

- 控制启停与仿真启停是两个独立操作。
- DISABLED 请求到达后立即拒绝新的手动切相位和配时控制命令。
- 当前绿灯必须完成原定时长，随后完成完整黄灯，再将所有 SUMO controlled links（包括四个右转 linkIndex 0、5、10、15）置为红灯。
- 全红确认后控制状态变为 DISABLED；SUMO 仿真继续 RUNNING，但信号控制不再推进。
- 从 DISABLED 重新启用时，AUTO 模式从确定的 NS_LEFT 初始业务阶段恢复；MANUAL 模式保持全红，等待人工请求。
- 仿真每次重新启动均重置控制域为 ENABLED/AUTO，并重置本次运行的阶段时间和灯色。
- 上述策略由 ADR-014 固化；过渡期间内部状态使用 DISABLING，避免将尚未完成的安全过渡误报为 DISABLED。

## 14. 浏览器控制台需求

控制台至少包含以下区域：

### 14.1 仿真控制

- 启动仿真。
- 停止仿真。
- 展示 STOPPED/STARTING/RUNNING/STOPPING/ERROR。
- 展示 SUMO 连接状态及错误信息。
- 重复启动、停止等非法操作应有明确反馈。

### 14.2 信号控制

- 展示信号控制 ENABLED/DISABLED。
- 启用/停用信号控制。
- 展示 AUTO/MANUAL 当前模式。
- 在仿真及控制状态允许时切换模式。
- 展示当前阶段、各信号组灯色、剩余时间及下一阶段。

### 14.3 手动相位操作

- 仅在 MANUAL 且控制 ENABLED、仿真 RUNNING 时开放操作。
- 展示合法目标阶段。
- 提交请求后展示 accepted/rejected、原因及实际过渡状态。
- 不允许通过 UI 绕过后端安全校验。

### 14.4 配时管理

- 展示当前生效配时及待生效配时。
- 分别编辑四类绿灯时长和对应黄灯时长：南北直行、南北左转、东西直行、东西左转。
- 校验最小值、黄灯正时长、相位过渡及计算出的红灯约束。
- 展示保存结果、生效时机和失败原因。
- 当前阶段不得因修改配时而被截断。

## 15. 二维/三维可视化需求

- 保留现有二维 SVG 路口视图，不因引入三维而删除或替换。
- 增加明确的“二维/三维”视图切换。
- 三维视图在浏览器中展示道路、车道、停止线、车辆和交通信号灯。
- 二维与三维共用同一份后端仿真状态和 WebSocket 数据，不得各自运行仿真或建立独立信号计时器。
- 车辆位置、角度、速度和车辆尺寸以 SUMO/后端数据为准。
- 三维道路及车道几何优先由 SUMO 网络 shape、lane width、junction shape、connection 等数据生成或转换。
- 三维场景应支持基本相机旋转、缩放和平移；提供俯视和斜视观察方式。
- 视图切换不得重置仿真、信号状态或控制模式。
- 三维首版优先保证几何、车道归属、车辆位置及灯色正确，不以照片级模型为验收前提。
