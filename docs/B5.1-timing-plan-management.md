# B5.1 手动配时方案管理

## 目标与术语

- **Default Timing**：首次初始化时冻结的服务器默认配时。
- **Saved Manual Plans**：MANUAL 模式下的命名方案库。
- **Active Timing**：AUTO/MANUAL 共用的当前生效配时。
- **Pending Timing**：已提交、等待安全边界的配时。
- **timing_version**：Active Timing 的运行版本号，不是方案 ID。

首次启动时，后端将 Settings 配时写入 `backend/data/timing_plans.json`；后续启动读取冻结值，不因 Settings 改动而覆盖。Docker 使用独立命名卷持久化该文件。

## 行为约束

1. AUTO 与 MANUAL 共用一个 `SignalService`、一个 `TimingService` 和同一份 Active Timing。切换模式或 ENABLED/DISABLED 不重置配时版本。
2. 保存当前草稿、删除方案只修改方案库，不修改 Active/Pending/timing_version。
3. 载入编辑区只修改浏览器草稿，不向后端提交。
4. 应用方案和恢复默认必须经过 `SignalService.submit_timing()`。MANUAL 已处于 ALL_RED 时允许安全立即应用；其他情况进入既有 pending/安全边界流程。
5. 恢复默认是把冻结的 Default Timing 作为新候选配时提交，不回滚历史版本。例如 Default v1 → 应用 A 后 Active v2 → 应用 B 后 Active v3 → 恢复 Default 后 Active v4。
6. 不修改四类受保护业务阶段顺序、八个绿/黄灯阶段和右转小写 `g` 让行逻辑。

## API

- `GET /api/signals/{tls_id}/timing-plans`
- `POST /api/signals/{tls_id}/timing-plans`，body: `{ "name": "晚高峰", "config": { ...TimingConfig... } }`
- `DELETE /api/signals/{tls_id}/timing-plans/{plan_id}`
- `POST /api/signals/{tls_id}/timing-plans/{plan_id}/apply`
- `POST /api/signals/{tls_id}/timing-plans/restore-default`

当前实现将方案库的列表、保存、删除、应用和恢复均限定在仿真 RUNNING、MANUAL、ENABLED 条件下。读取/保存/删除通过 lifecycle 的 `read_state` 锁；应用/恢复通过 `run_control_action`。如后续希望 STOPPED 或 DISABLED 时仍能管理方案库，需要单独调整业务策略与前端提示，不应绕过生命周期锁。

## 存储与并发边界

JSON 文件使用临时文件 + `os.replace` 原子替换，并由 `threading.RLock` 保护当前进程内的读写。此设计仅适用于当前单容器/单 Uvicorn worker 部署，不具备多进程/多副本协调能力。未来启用多 worker 或多副本时应迁移到 PostgreSQL 或共享存储。

## 集成步骤

在项目根目录运行包内 `Apply-B5.1-Integration.ps1`。脚本会先检查所有目标文件和锚点，再执行精确修改；如果目标内容与采集版本不一致、锚点缺失/重复或新文件已存在且内容不同，会中止，不会强行覆盖。
